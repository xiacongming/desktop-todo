## 1. 长内容编辑：自动增高 + 手动放大

### 1.1 新增输入框

`index.html` footer 里 `<input id="input">` → `<textarea id="input" rows="1">`。

行为：
- 内容为空时 1 行高（约 30px），随换行/自动折行增高，最高到窗口高度的 40%（`min(8 行, 40vh)`），超过后内部滚动。
- 键盘：`Enter` 提交；`Shift+Enter` 换行；中文输入法 `isComposing` 期间回车不提交（现有判断保留）。
- 提交后高度复位到 1 行。

### 1.2 行内编辑

`rowHTML()` 里的 `<input class="edit-input">` → `<textarea class="edit-input">`，同样自动增高，最高 12 行。

- `Enter` 保存、`Shift+Enter` 换行、`Esc` 取消（与新增相反，因为编辑时更常需要多行）。
- 进入编辑态时给行加 `data-editing="1"`，CSS 里 `.row[data-editing="1"] { draggable: false }` 无效——必须改 JS：`draggable="${t.done || editing ? 'false' : 'true'}"`，并在 `dragstart` 里再拦一层。

### 1.3 手动放大（用户明确要的）

两处入口，共用同一套逻辑：

1. **拖拽上边缘**：composer 顶部加 6px 高的手柄，拖动改变输入框高度（`mousedown` + `mousemove` 算差量），松开后记住高度（存 `settings.composerHeight`，下次启动恢复）。
2. **双击输入框**：在「1 行紧凑」和「40% 窗口高度」之间切换。

> 不做「弹独立大编辑窗口」，因为对一个常驻小挂件来说，多一层窗口会让「随手记」变成负担。

### 1.4 多行内容的显示

`.text` 需要 `white-space: pre-wrap`，否则存进去的换行会塌成一行。

## 2. 列表内长内容折叠/展开

### 2.1 判定与入口

`.text` 保持 `line-clamp: 3`，但判断「要不要显示展开按钮」不能只看 DOM 高度——

> **测试环境限制**：`test/renderer.test.js` 用 jsdom，jsdom 不做布局计算，`scrollHeight` / `clientHeight` 恒为 0。纯靠 `scrollHeight > clientHeight` 判定的话，真实环境能跑、测试里永远不显示按钮。

所以采用**内容启发式 + 布局复核**双层判定：

```js
function needExpand(text) {
  const lines = text.split('\n').length;
  return lines > 3 || text.length > 110;   // 110 ≈ 3 行中文（13px / 340px 宽）
}
// 真实环境里再补一次布局复核，窄窗口下短文本也可能溢出
if (!needExpand(t.text)) {
  const n = textEl.scrollHeight > textEl.clientHeight + 1;
  needExpand = n;
}
```

溢出才插入：

```html
<button class="more" data-act="more">展开</button>
```

- 展开态加 class `expanded`，CSS 去掉 clamp；按钮文案变「收起」。
- 展开状态存 `const expanded = new Set()`（内存，不落盘），重渲染后仍在——否则点一下别的地方就收回去，很难用。
- 超长内容仍按 500 字上限截断，不额外处理。

### 2.2 已知坑

判断溢出必须在 DOM 插入**之后**做，且窗口宽度变化时要重算（`resize` 事件 + 200ms debounce）。否则窄窗口下明明溢出了却不显示按钮。

## 3. 搜索

### 3.1 交互

- 顶部栏加放大镜按钮；`Ctrl+F` 也唤起。点击后搜索条从 header 下滑展开，输入框自动聚焦。
- 输入即搜（100ms debounce），`Esc` 清空并收起。
- 匹配范围：`text` 全文，大小写不敏感，多关键词用空格分隔按「全部命中」处理（`foo 密码` 同时含两者）。
- 搜索时**已完成区也参与**，并在结果里用不同底色标出「已完成」，否则搜「以前的账号」会搜不到。
- 搜索态下禁用拖拽排序（顺序已无意义），并隐藏置顶分区逻辑，平铺展示，按 `order` 排。

### 3.2 高亮实现

不能直接把用户输入塞进 `innerHTML`。做法：

```js
function highlight(text, terms) {
  // 1. 把 text 按命中区间切片
  // 2. 每片先 esc()，命中片包 <mark>
  // 3. 拼接返回
}
```

必须保证转义在切片之后逐段执行，不能先转义再按位置切（`&amp;` 长度会变，位置全错）。

### 3.3 显示「N 条结果」，无结果时给出空状态文案。

## 4. 循环提醒（闹钟）

### 4.1 数据模型

在 todo 上扩展，不新建独立实体（理由见 6.1）：

```js
{
  dueAt: '2026-10-28T09:30:00.000Z',   // 首次/下一次触发时刻（现有字段）
  repeat: null | {
    type: 'daily' | 'weekdays' | 'weekly' | 'interval',
    weekday: 1,        // type=weekly 时有效，1=周一…7=周日
    intervalMin: 30    // type=interval 时有效，最小 5 分钟
  },
  firedAt: null        // 上一次实际触发的 ISO 时间，替代语义含糊的 remindedAt
}
```

- `version: 1 → 2`。旧数据无 `repeat` 即单次，`remindedAt` 保留读入，首次保存时迁移为 `firedAt`。
- 不删 `remindedAt` 字段（避免旧版本回退时丢数据），只是不再写。

### 4.2 下一次触发时间计算

纯函数 `nextOccurrence(fromISO, repeat, now)`，放在 `src/main/recurrence.js`，**独立单测**：

| type | 规则 |
|---|---|
| `daily` | 每天同一时刻；若 `from` 已过今天该时刻，顺延到明天 |
| `weekdays` | 周一至周五同一时刻，周六周日顺延到周一 |
| `weekly` | 每周指定 `weekday` 同一时刻 |
| `interval` | `from + intervalMin 分钟`，但要按整点对齐（09:00 起 30 分钟 → 09:30、10:00…），否则关一次机就全乱 |

必须覆盖的边界：跨月、跨年、闰年 2 月 29 日、`weekday` 落在周末、`interval` 跨零点。

### 4.3 调度

改造 `checkReminders()`（`main.js:305`）：

```
现在：dueAt <= now 且 remindedAt 为空 → 提醒 → 写 remindedAt（此后永不再提醒）
改成：dueAt <= now → 提醒 → 
      repeat 存在 ? dueAt = nextOccurrence(now, repeat) : 不推进（firedAt 置位，等同现状）
```

**幂等**：判定条件是 `dueAt <= now`，触发后 `dueAt` 立即前移到未来，所以 20 秒轮询同一周期内不会重复弹。不要用 `firedAt` 做判定条件。

**错过多次只补一次**：关机 3 天后开机，「每天 9 点」的那条不应弹 3 次。`nextOccurrence` 里循环推进直到 `> now`，只提醒一次，文案注明「（已跳过 2 次）」。

**睡眠唤醒**：`setInterval` 在睡眠期间不累计，但判定用的是 `Date.now()`，唤醒后第一轮就会补上。不需要额外处理，但要确认 `powerMonitor` 的 `resume` 事件里手动触发一次检查，避免唤醒到下一轮 20s 之间的空窗。

### 4.4 UI

扩展现有的「截止时间」浮层（`#duePop`），不新开一个：

```
截止时间：[datetime-local]
重复：  [不重复] [每天] [工作日] [每周] [自定义间隔]
        选「每周」→ 出现星期选择器
        选「自定义间隔」→ 出现分钟输入（预设 15/30/60/120）
快捷项：今天 18:00 / 明天 09:00 / 下周一 09:00（保留）
```

条目上的徽标文案要体现重复：`每天 09:30`、`工作日 09:30`、`每 30 分钟`、`明天 09:00`。逾期态对重复项不适用（自动推进了），改显示「已提醒，下次 明天 09:30」。

### 4.5 停止提醒

三种方式：勾选完成（自动停）、浮层里选「不重复」+ 清空时间、行内新增一个「关闭闹钟」的小铃铛按钮（悬停出现）。

## 6. 需要你确认的三个决策

### 6.1 循环提醒挂在哪？

**建议 A（推荐）**：作为待办属性，一个待办一条提醒。
理由：你描述的场景（交房租、每日打卡、账号定期改密）本身就是"一件事"，不需要独立实体；UI 复用现有浮层，改动面小。

**方案 B**：独立「闹钟」列表，与待办分开。
好处是闹钟不需要"完成"这个动作，纯粹的定时器。代价是要新增一个分区、一套增删改 UI、一套排序，工作量约多 1.5 倍。

### 6.2 Enter 键语义

新增框：**Enter 提交 / Shift+Enter 换行**（保持现有肌肉记忆）。
行内编辑：**Enter 保存 / Shift+Enter 换行**（编辑时更常需要多行）。
若你更希望「Enter 换行、Ctrl+Enter 提交」，现在说，两处一起改。

### 6.3 账号密码是否要遮挡？

你说要在待办里存系统账号密码。当前实现是 **`%APPDATA%\StickyTodo\todos.json` 明文**，任何人拿到这台电脑或这个文件就能直接读。

两个选项：
- **加「遮挡」标记**：这类条目在列表里显示为 `prod-db · ••••••`，点一下才展开，搜索仍能命中（但高亮不显示明文）。防止的是"别人路过看到屏幕"，**不防"文件被拷走"**。
- **不建议存密码**：真正要存密码用专门的密码管理器。如果只是记"账号是 admin，密码见密码管理器"，那在当前功能里完全够用。

我倾向：**加遮挡 + 在 README 里明确写清"这不是密码管理器"**。不要给用户一个虚假的安全感。

## 8. 明确不做的

- **不做云同步**（v1.0 已定的本地优先策略不破）
- **不做提醒声音自定义**（Windows 系统通知声音够用，自定义要引音频文件，破坏"零依赖"）
- **不做搜索历史/模糊纠错**（200 条以内直接过滤即可，加这些是过度设计）
- **不改打包方案**（体积问题另议，见上一轮讨论）
